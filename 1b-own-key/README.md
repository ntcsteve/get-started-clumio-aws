# Step 1b: Use your own key (optional, permanent)

**Preview: not yet applied live.** Part of [Get started with Clumio on AWS](../README.md). Run it after [step 1](../1-connect-clumio/README.md), in a terminal set up as in [Before you begin](../README.md#before-you-begin).

**Do you need it?** Only if a rule you follow, such as a regulator, an audit framework or a contract, requires your backups to be encrypted with a key you manage. Otherwise skip this step: Clumio encrypts every backup with its own keys.

**What it does.** From this step on, Clumio encrypts every SecureVault backup with your AWS KMS key. S3 and RDS backups use your key only. EC2 and EBS backups use your key together with Clumio's own. Backups taken before stay on Clumio's keys, so run it after step 1 and before step 2.

**It's permanent.**

- Your Clumio tenant stays bound to this key and this AWS account. You can't change either later. Turning the feature off takes a request to Clumio support.
- Every backup encrypted with the key needs it for as long as the backup is kept. If the key, or its AWS account, is deleted, those backups are lost for good. AWS waits 7 to 30 days before it deletes a key, and you can cancel in that time.
- Clumio makes replicas of the key in the Regions where it keeps backups. If the key or a replica is disabled, backups and restores that need it stop until you enable it again.
- After you apply, never change `key_id` or `iam_prefix`. The step refuses any plan that would, because Clumio's role and alias must stay as they are.

**What you need.** Set `1b-own-key/terraform.tfvars`:

- `account_id`: the account from step 1.
- `clumio_region`: your Clumio control-plane Region, set when your Clumio account was created. It's often not where your data is. Find it from your portal, in the table in [Before you begin](../README.md#before-you-begin).

- `key_id`: your key's ID (`mrk-...`). It must be a customer-managed, symmetric, multi-Region primary key, enabled, in `clumio_region` and in this account. The plan checks each of these and stops, before anything is created, if one fails.
- `iam_prefix`: as in step 1, if your IAM role names need a prefix.
- `i_understand_byok_is_permanent = true`, once you've decided.

You also need an AWS sign-in that can describe the key, create an IAM role with an inline policy (`iam:CreateRole`, `iam:PutRolePolicy`), and create an alias on the key (`kms:CreateAlias`). Step 0 doesn't preview this step.

**No key yet?** Create one in `clumio_region` with two commands. The key stays outside Terraform, so nothing in this repository can delete it. AWS's default key policy lets IAM in your account grant Clumio access.

```bash
aws kms create-key --multi-region --region <clumio_region> \
  --description "Clumio BYOK: deleting this key loses the backups it encrypts" \
  --query KeyMetadata.KeyId --output text
aws kms enable-key-rotation --key-id <the mrk-... ID it printed> --region <clumio_region>
```

**Where the key can come from.**

| Key source | Works with Clumio | What to know |
|---|---|---|
| AWS KMS key, material generated by AWS | Yes | AWS copies the material to each replica Region. With rotation on, it rotates yearly. |
| AWS KMS key, material imported from an HSM or key manager, such as Fortanix, Thales or Entrust | Yes, with more work; not yet tested live | The material must never expire. You must import the same material into each replica Region Clumio adds. There's no automatic rotation. |
| AWS CloudHSM key store, or an external key store | No | AWS can't create multi-Region keys in a custom key store. |

**Before you run it.**

- Clumio's setup module creates the IAM role `ClumioKMSRole` (or `<iam_prefix>-ClumioKMSRole`) at path `/`. It takes no permissions boundary and no tags. It also adds the alias `alias/clumio-byok` to your key. [SECURITY.md](../SECURITY.md#step-1b-your-own-key) lists what the role can do.
- Clumio's replicas of your key, described above, belong in your data-residency review.

**Run it.**

```bash
cd 1b-own-key
terraform init
terraform plan
terraform apply
terraform plan
```

**What you should see.** The second plan says *No changes*. The Encryption Key page in the Clumio console shows your key. After the next backup, CloudTrail shows KMS calls on your key from Clumio's role sessions, with the names Clumio's CloudTrail documentation lists, such as `KMS-backup`: that's Clumio using it.

**If something goes wrong.** *Key ... must be ...*: the key failed a check, and nothing was created; fix the key or `key_id`. *BYOK is permanent: read README.md in 1b-own-key*: set `i_understand_byok_is_permanent = true` once you've decided. *NotFoundException* reading the key: the key isn't in `clumio_region`, or not in this account. *Instance cannot be destroyed*: the plan would remove or change BYOK, which can't be undone; put `key_id` and `iam_prefix` back. If an apply stops partway, for example because `alias/clumio-byok` already exists, fix the cause and apply again.
